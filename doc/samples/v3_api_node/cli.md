# MWC owner API CLI: developer and exchange guide

This guide starts with no assumed MWC or JavaScript knowledge. It explains how
to connect the Node.js sample to a test wallet, inspect its data and exercise the
wallet's owner API. All examples use **Floonet**, MWC's public test network.
Floonet coins are test coins; use a dedicated test wallet for this walkthrough.

## What runs where

Three programs cooperate:

| Program | Responsibility | Floonet connection |
| --- | --- | --- |
| `mwc` (mwc-node) | Connects to peers, validates/synchronizes the blockchain, and accepts finalized transactions. | Its node API normally listens on port **13413**. |
| `mwc-wallet owner_api` | Holds the wallet database and encrypted seed; selects outputs, builds/signs transactions and asks the node about the chain. | Its owner API normally listens on port **13420**, path `/v3/owner`. |
| This Node.js CLI | Sends commands to the wallet owner API and displays the replies. | Connects to the wallet, which contacts the node. |

**Start mwc-node and keep it running while testing.** The wallet needs a working
connection to that node to refresh balances, scan outputs and post transactions.
Starting the owner listener or opening the wallet alone does not establish that
the node connection works. The node and wallet must use the same network.

The CLI does not synchronize a blockchain or directly access the wallet seed
file. Opening the wallet authorizes the wallet process to use its keys; the
wallet returns an in-memory token for subsequent commands. The CLI keeps that
token private and closes the wallet when it exits normally.

**Owner API** means the privileged API controlled by the wallet's owner. The
**Foreign API** handles interaction with another wallet, including accepting an
incoming send. This CLI uses only the owner API. `receive`, `finalize_invoice`,
listener control, mining and swaps are therefore not CLI commands here.

There are two distinct credentials:

- `.owner_api_secret` authenticates **this client → wallet**. It is a secret file
  generated by the wallet, not your wallet password.
- The node's `.foreign_api_secret` authenticates **wallet → node**. The wallet's
  `node_api_secret_path` must reference the matching node credential. If the
  wallet and node use separate `.foreign_api_secret` files, both files must
  contain the **same secret**.

Your **wallet password** unlocks the wallet's encrypted seed. Your **recovery
phrase** can restore the wallet and must remain private. Neither belongs in a
command-line argument or a checked-in file.

## Vocabulary used by the commands

| Term | Meaning |
| --- | --- |
| Output | A spendable piece of wallet balance. A transaction consumes existing outputs and creates new ones. |
| Confirmation | A block added after the transaction's inclusion, including its inclusion block according to the wallet's confirmation calculation. More confirmations reduce exposure to chain reorganization. |
| Slate | Transaction data passed between participants while they jointly construct a transaction. |
| Slatepack | A packaged slate. An encrypted Slatepack is addressed to a recipient's public Slatepack address. A file containing it is not a completed payment by itself. |
| Finalize | Complete the sender's transaction after receiving the recipient's reply. |
| Post | Broadcast a finalized transaction to the node. Posting does not mean the transaction is confirmed. |
| Late locking | Defer selecting/locking spend inputs until finalization. Useful when a recipient may take time to reply. The wallet must still have enough spendable funds when finalizing. |
| Change output | An output returning excess input value to the sender. `--change_outputs` sets the target count. |
| Wallet transaction ID | A small integer meaningful inside this wallet, selected with `--id`. |
| Slate UUID | The transaction's UUID shared between participants, selected with `--txid`. |
| nanoMWC | The smallest accounting unit: **1 MWC = 1,000,000,000 nanoMWC**. |

## Prerequisites

Install Node.js 22 or newer, including `npm`, using the
[Node.js download instructions](https://nodejs.org/en/download). Node.js runs
JavaScript outside a browser. `npm` runs the commands defined in this sample's
`package.json`; this sample has no third-party npm dependencies to install.

You also need compatible builds of `mwc` and `mwc-wallet` available in your
terminal. Use the current wallet source revision that accompanies this sample:
its encrypted API uses authenticated envelope metadata which older clients and
servers may not implement. See [wallet setup](../../setup.md) for wallet
installation and the [Floonet node guide](https://github.com/mwcproject/mwc-node/blob/master/doc/mwc_floonet.md)
for node installation and synchronization.

```sh
node --version
npm --version
mwc --version
mwc-wallet --version
```

Each command should print its installed version. Node must report `v22` or
higher. If a command is missing, add the directory containing that executable
to your terminal's `PATH`. For a source build, the wallet executable is normally
`mwc-wallet/target/release/mwc-wallet` and the node is `mwc-node/target/release/mwc`.

The shell commands below are for macOS/Linux. On Windows, use equivalent shell
environment-variable syntax and restrict access to the test-wallet directory
with Windows file permissions. The JavaScript client itself uses Node.js
platform APIs.

## First session on Floonet

### 1. Start a node in terminal A

If you already have a synchronized Floonet node, keep it running and note its
API address and `foreign_api_secret_path` in `mwc-server.toml`. Otherwise:

```sh
mkdir -p "$HOME/mwc-api-test/node"
cd "$HOME/mwc-api-test/node"

# First run only: create this node's configuration.
mwc --floonet server config

# Keep this process running in terminal A.
mwc --floonet server run
```

Expect configuration/data files in this directory and a running node display.
Wait until the node reports **Running** and is synchronized with its peers.
Initial synchronization can take a substantial amount of time. For this setup,
the node credential is normally
`$HOME/mwc-api-test/node/.foreign_api_secret`; use the configured value if it
was changed. The node and wallet must both use Floonet.

### 2. Create and configure a wallet in terminal B

Skip initialization if you already created the test wallet from the main
README. Set the directory variable to the existing wallet instead.

```sh
export MWC_SAMPLE_WALLET_DIR="$HOME/mwc-v3-sample"
mwc-wallet --floonet --top_level_dir "$MWC_SAMPLE_WALLET_DIR" init
```

Choose a test password when prompted and save the recovery phrase privately.
The command creates `mwc-wallet.toml`, credential files and a `wallet_data`
directory. An empty wallet is sufficient for queries and API connection tests.

Open `$HOME/mwc-v3-sample/mwc-wallet.toml` in a text editor. Edit the existing
values under `[wallet]` (do not create a second `[wallet]` section):

```toml
owner_api_include_foreign = false
owner_api_include_mqs_listener = false
check_node_api_http_addr = "http://127.0.0.1:13413"
```

Set `node_api_secret_path` to the **node's** credential file, with an absolute
path. This command prints the exact TOML line for the node directory above;
copy its output into the existing setting:

```sh
printf 'node_api_secret_path = "%s/mwc-api-test/node/.foreign_api_secret"\n' "$HOME"
```

If your existing node uses the default directory, use its
`$HOME/.mwc/floo/.foreign_api_secret` instead. TOML does not expand `$HOME` or
`~`; paste the actual absolute path. Keep `api_secret_path` pointing to the
wallet's own `.owner_api_secret`.

Alternatively, keep the wallet's generated `node_api_secret_path` pointing to
its own `.foreign_api_secret` and copy the **node's** secret into that file:

```sh
# Alternative to pointing node_api_secret_path directly at the node's file.
cp "$HOME/mwc-api-test/node/.foreign_api_secret" "$MWC_SAMPLE_WALLET_DIR/.foreign_api_secret"
chmod 600 "$MWC_SAMPLE_WALLET_DIR/.foreign_api_secret"

# Verify the contents without printing the secret; success prints nothing.
cmp "$HOME/mwc-api-test/node/.foreign_api_secret" "$MWC_SAMPLE_WALLET_DIR/.foreign_api_secret"
```

Use the paths configured for your node and wallet if they differ. A separately
generated wallet secret is not sufficient: the contents must match the node's
file configured by `foreign_api_secret_path`. Update the wallet's copy whenever
that node secret changes. Restart the wallet listener after changing its node
address, secret path or copied secret.

### 3. Get Floonet test coins and start the wallet listener

Keep the synchronized Floonet node running in terminal A. In terminal B, before
starting the owner listener, request **3 test MWC** for the wallet just created:

```sh
mwc-wallet --floonet --top_level_dir "$MWC_SAMPLE_WALLET_DIR" faucet_request --amount 3

# Refresh from the node and inspect the resulting balance.
mwc-wallet --floonet --top_level_dir "$MWC_SAMPLE_WALLET_DIR" info
```

Enter the wallet password when prompted. `faucet_request` starts the required
MWCMQS connection, requests funds from the Floonet faucet, then finalizes and
posts the returned transaction automatically. The wallet limits each request
to **5 MWC**. Expect `Command 'faucet_request' completed successfully` on success;
this means the transaction was posted, not that it is already confirmed.

In the `info` output, look for the requested amount under **Awaiting
Confirmation** initially, then **Currently Spendable** once enough blocks have
confirmed it. The default minimum is 10 confirmations. Repeat `info` after more
blocks arrive; the exchange walkthrough uses a stricter 1440-confirmation
policy. An empty wallet is enough for API/query tests, so funding is needed only
when testing payments.

If the faucet has been idle, it may need a few minutes to synchronize. Check
wallet history with `txs` before repeating a request after an uncertain result.
See the [Floonet faucet guide](../../floonet_faucet.md) for service details and
how to return unused test coins. This sample does not verify live faucet
availability.

If the owner listener is already running for this wallet, exit the Node.js CLI,
stop that listener with Ctrl+C, run the native faucet and `info` commands, then
restart the listener. Use one wallet process at a time for this directory.

Start the owner listener in terminal B:

```sh
mwc-wallet --floonet --top_level_dir "$MWC_SAMPLE_WALLET_DIR" owner_api
```

Expect the owner listener to start on `127.0.0.1:13420`. Leave it running. With
the configuration above, this listener starts with the wallet closed; the
Node.js CLI will ask for its password when you run `open`.

### 4. Start the JavaScript CLI in terminal C

Change to **this checkout's** `doc/samples/v3_api_node` directory. For example,
from the root of your current `mwc-wallet` source checkout:

```sh
cd doc/samples/v3_api_node
npm run cli -- help
```

Expect a command list headed `MWC Owner API CLI`. This help command works
without any wallet connection or credentials. `Missing script: cli` means you
are in another/older checkout: inspect `pwd` and that directory's `package.json`.

Set the connection and secret-file path:

```sh
export MWC_OWNER_API_URL='http://127.0.0.1:13420/v3/owner'
export MWC_OWNER_API_SECRET_FILE="$HOME/mwc-v3-sample/.owner_api_secret"
npm run cli
```

Expect:

```text
Connecting to the owner API...
[wallet-api] {"direction":"request","method":"init_secure_api","body":...}
Connected. Type open to unlock the wallet, help for commands, or exit to close.
mwc-wallet>
```

The handshake body above is abbreviated; the CLI prints a JSON request record.
The `mwc-wallet> ` text is the CLI prompt whenever it is waiting for a command,
whether the wallet is open or closed. Type the following commands **inside
that prompt**, one at a time; do not type the prompt itself:

```text
open
info
account
address
txs --count 10
close
exit
```

`open` asks for the wallet password without displaying it. Empty passwords are
supported by pressing Enter. A successful open prints `"wallet": "open"`.
`info` refreshes the wallet against the node and prints balances such as:

```json
{
  "refreshed": true,
  "height": "1757000",
  "minimum_confirmations": "10",
  "total_mwc": "0.000000000",
  "spendable_mwc": "0.000000000",
  "locked_mwc": "0.000000000",
  "awaiting_confirmation_mwc": "0.000000000"
}
```

These numbers are illustrative. An empty wallet has zero balances. `refreshed`
reports whether the wallet successfully refreshed against the node; `false`
means you are looking at an unvalidated/cached view. `info --no-refresh` requests
the local cached view explicitly. Refresh uses the wallet's ordinary scan and
replay-protection behavior; it is more than reading a static database field.

Before each network operation, the CLI prints `Requesting METHOD...` and a
`[wallet-api]` JSON record containing the outgoing request. For example, `info`
produces a record like this (formatted here for readability):

```json
{
  "direction": "request",
  "method": "retrieve_summary_info",
  "body": {
    "jsonrpc": "2.0",
    "id": "2",
    "method": "retrieve_summary_info",
    "params": {
      "token": "[REDACTED]",
      "refresh_from_node": true,
      "minimum_confirmations": 10
    }
  }
}
```

Request IDs are generated by the client. The request shown is the JSON before
encryption, with secrets removed; it is sent inside an encrypted v3 envelope.
Passwords, tokens, private keys and sensitive configuration are redacted. Long
values are bounded and marked as truncated. Request records go to standard
error, keeping standard output usable for result JSON.

An API error returns you to the prompt while the secure
session remains usable. A transport/authentication failure ends the session;
inspect the wallet/transaction state before starting again.

`close` locks this session's wallet but leaves the CLI connected. `exit`, Ctrl+D
at the prompt, or Ctrl+C initiates cleanup and closes a wallet opened by this
CLI. A request already running may finish or reach its timeout before cleanup.
If closing cannot be confirmed, the CLI reports that explicitly.

## Running one command from a script

Supplying a command after `--` runs it once and exits. The CLI opens the wallet
when the command needs it and closes it afterward. Passwords can come from a
hidden terminal prompt or the `MWC_WALLET_PASSWORD` environment variable.

```sh
# Run a single query and answer the hidden password prompt.
npm run cli -- info --min_conf 1440
```

For scripts or redirected input, supply the password through the environment.
This example reads it privately in a child Bash shell and captures JSON output:

```sh
bash -c 'umask 077; read -r -s -p "Wallet password: " MWC_WALLET_PASSWORD; printf "\n"; export MWC_WALLET_PASSWORD; npm run --silent cli -- info --no-refresh >balance.json'
```

`balance.json` contains the result JSON. Progress and errors go to standard
error, so they do not corrupt the JSON result. `--silent` suppresses npm's own
script banner. Exit code 0 means success; exit code 1 means a reported failure.
The password is removed from the Node.js process environment after loading and
consumed on its first password request. A later `open` asks again.

Mutating commands ask for an explicit confirmation in a terminal. For reviewed,
intentional automation, add `--yes`. For example, a scripted cancellation is
`npm run --silent cli -- cancel --id 12 --yes`. This changes wallet state;
select the actual intended transaction, not the illustrative ID.

A successful HTTP request is not a business-level guarantee of confirmation.
After sending a transaction, track the UUID through `txs` and your node until
your integration's required confirmations have accumulated.

## CLI conventions

- Use `help COMMAND` or `COMMAND --help` to see accepted flags. Unknown commands,
  unknown flags and duplicate flags are rejected, except repeatable `rpc --param`.
  `help rpc METHOD` lists the exact API parameter names for a method.
- Use quotes around a label or filename containing spaces. The interactive
  prompt supports quoting/backslash escaping; it does not execute shell commands
  or expand `$HOME`, `~`, pipes or command substitutions. Use an absolute path
  or a path relative to the directory where you started the CLI.
- Slatepack/JSON input commands accept `--content` as an alternative to a file.
  Quote the whole value. An unfinished quote produces a `...> ` continuation
  prompt, allowing a multiline Slatepack to be pasted. Enter passwords
  separately when the hidden password prompt appears.
- Data commands accept `--out FILE` to save JSON. Outputs are new files with
  owner-only permissions on macOS/Linux. Existing files and symlinks are rejected.
- Wallet-data commands accept `--account LABEL`. In interactive mode it changes
  the active account for subsequent commands too. `open --account LABEL` selects
  the initial account; `account --switch LABEL` changes it explicitly.
- `send` and `invoice` amounts are MWC decimals, for example `1.25`. At most nine
  digits may follow the decimal point. Conversion uses exact integer arithmetic;
  exponential notation, negative amounts and the native wallet's `max` shorthand
  are not accepted by these convenience commands.
- API-level JSON amounts are generally nanoMWC decimal strings. Plain ID/count
  parameters use JSON numbers. See the [API client reference](readme.md#amounts-and-transaction-construction).
- The default confirmation setting is 10. Set your own policy explicitly; the
  exchange examples below use 1440. Floonet testing can use a different policy.

### Paste content instead of reading a file

`unpack`, `finalize` and `pay` accept the same Slatepack text or versioned-slate
JSON from `--content` that they accept from `--file`. For example, replace the
placeholder below with the complete received Slatepack:

```text
unpack --content 'BEGINSLATEPACK. REPLACE_WITH_COMPLETE_SLATEPACK_BODY .ENDSLATEPACK.'
```

Then use `finalize --content 'COMPLETE_RESPONSE' --dest finalized.json --nopost`
for a send response, or `pay --content 'COMPLETE_INVOICE' --dest response.slatepack`
for an invoice. The same purpose, direction, sender and transaction checks apply
as for file input. These strings are placeholders, not test transactions.

`post --content 'TRANSACTION_JSON'` accepts finalized transaction/slate JSON;
`verify_proof --content 'PROOF_JSON'` accepts payment-proof JSON. Choose exactly
one input source: supplying both a filename and content is an error. Inline
input and input files are limited to 8 MiB. `unpack --address_index N` forwards
the chosen address index to `decode_slatepack_message`; omit it for the wallet's
current index. For the full underlying API controls, use `rpc` below.

## Command reference

The familiar command names are a subset of the native wallet CLI. The
following descriptions specify this implementation's behavior.

### Connection and wallet lifecycle

| Command | Behavior |
| --- | --- |
| `help` / `help NAME` / `help rpc METHOD` | General help, command options, or exact API parameter names. |
| `open [--account LABEL] [--name NAME]` | Hidden password prompt; stores the returned wallet token privately. Rejects opening twice in one session. Optional `name` is forwarded to the API. |
| `close [--name NAME]` | Calls `close_wallet` and clears the local token on success. Defaults to the name used when opening; an explicit name must match it. |
| `exit` / `quit` | Closes the wallet opened by the session and exits. |
| `recover --out FILE [--name NAME]` | Prompts for the password and exports the recovery phrase to a new private text file. It does not restore a wallet. |

Create/recover a new wallet with the native initialization command or the
explicit `rpc create_wallet` method. The owner API's `create_wallet` argument
`mnemonic_length` is entropy **bytes**, not word count: 16 produces 12 words,
32 produces 24. Handle a supplied recovery phrase as a secret.

### Accounts and queries

| Command | Options and result |
| --- | --- |
| `info` | `--min_conf N` (`-c`), default 10; `--no-refresh` requests cached data. Returns named balances in MWC. |
| `outputs` | `--show_spent` (`-s`) includes spent outputs; `--no-refresh` uses the cache. Returns `[refreshed, outputs]`. |
| `txs` | `--id N` (`-i`) or `--txid UUID` (`-t`) selects one transaction. `--count N` (`-c`) requests the newest N entries instead. `--show_last_four_days` includes recent/pending history. `--no-refresh` uses the cache. Returns `[refreshed, transactions]`. |
| `account` | List account labels and derivation paths. `--create LABEL` (`-c`) creates one; `--switch LABEL` selects one. |
| `address` | Returns the wallet's current Slatepack and MQS public addresses. Use the Slatepack `public_key` for encrypted Slatepacks. |
| `node_height` | Returns node height and whether the node was contacted. |

An account partitions the wallet's derived keys and transaction history. It
shares the same underlying wallet seed. Changing the active account changes
which account the following wallet operations use.

### Withdrawal construction

```text
send AMOUNT --dest FILE --slatepack_recipient ADDRESS [OPTIONS]
```

`ADDRESS` is the canonical 56-character Slatepack public address, without an
`http://` prefix or `.onion` suffix. The CLI validates its encoding/checksum
before creating a transaction. This command creates an encrypted Slatepack
file for delivery by your application. It does not deliver it or broadcast a
transaction automatically.

| Option | Meaning |
| --- | --- |
| `--dest FILE` (`-d`) | New output file. `--out` is an alternative name. |
| `--slatepack_recipient ADDRESS` | Intended recipient of the encrypted Slatepack. |
| `--late-lock` (`-l`) | Select/lock inputs at finalization. Without it, lock outputs after creation. |
| `--estimate` (`-e`) | Estimate fees/selection with `estimate_only`; creates no outgoing Slatepack and needs no destination or recipient. |
| `--min_conf N` (`-c`) | Spendability confirmation threshold, default 10. |
| `--change_outputs N` (`-o`) | Target change-output count, default 1. The wallet determines the actual resulting outputs. |
| `--selection smallest\|all` (`-s`) | Input selection strategy, default `smallest`. |
| `--max_outputs N` | Soft input-selection limit, default 500. |
| `--ttl_blocks N` | Transaction lifetime in blocks, passed to the wallet. |
| `--message TEXT` (`-g`) | Participant message. This can be included in data exchanged with the other party. |
| `--amount_includes_fee` | Treat the supplied amount as including the fee. |
| `--min_fee N` | Minimum fee in nanoMWC, supplied as a safe integer. |
| `--yes` (`-y`) | Execute without the interactive confirmation. |

For successful sends, the command also creates `FILE.recovery.json`, containing
the initial slate, transaction UUID, recipient and late-lock setting. This file
is a local workflow checkpoint, not the message to send to the recipient.

### Completing and tracking a withdrawal

| Command | Behavior |
| --- | --- |
| `unpack --file FILE [--out JSON]` | Decodes Slatepack purpose, sender, recipient and slate. Accepts `--content TEXT` instead of `--file`; optional `--address_index N` selects the decode index. Also reads plain versioned-slate JSON. Inspection alone does not sign or post. |
| `finalize --file RESPONSE --dest FINALIZED [--nopost] [--fluff]` | Accepts `--content TEXT` instead of `--file`. Checks the incoming Slatepack direction/purpose, the wallet's outstanding send, and the stored recipient when present. Verifies participant messages, finalizes, saves the final slate, and posts unless `--nopost` is set. |
| `post --input FILE [--fluff]` | Accepts `--content JSON` instead of `--input`. Broadcasts a finalized JSON transaction or a JSON slate containing `tx`. Binary `.mwctx` files and raw Slatepack text are not this command's input format. |
| `repost --id N [--fluff]` | Retrieves and broadcasts a stored transaction. `--txid UUID` is also accepted. |
| `repost --id N --dumpfile FILE` | Exports the stored transaction JSON without broadcasting. |
| `cancel --id N` / `cancel --txid UUID` | Cancels an unconfirmed wallet transaction and allows the wallet to release applicable locks. It cannot undo an already confirmed payment. |

`--fluff` asks the node to broadcast directly instead of the normal Dandelion
relay phase. Use the ordinary default unless your test specifically needs it.
`finalize` saves its result before posting and also leaves a recovery JSON file.
`post`/`repost` success means the node accepted the posting request; confirmation
is a separate event.

### Invoice, proof and recovery operations

| Command | Behavior |
| --- | --- |
| `invoice AMOUNT --dest FILE --slatepack_recipient ADDRESS` | Creates an encrypted invoice and a local recovery checkpoint. Accepts `--message`. The specified recipient is the payer. |
| `pay --file INVOICE --dest RESPONSE` | Accepts `--content TEXT` instead of `--file`. Decodes/verifies the invoice, confirms its amount, processes it, locks participant 1's outputs, and exports the response. Accepts `--min_conf` (`-c`), `--change_outputs`, `--selection`, `--max_outputs`, `--min_fee` and `--message`. The invoice fixes the amount; TTL, fee-included amounts, late locking and estimates are not options for this command. It does not post. |
| `export_proof FILE --id N` / `--txid UUID` | Exports the payment proof for that transaction. |
| `verify_proof FILE` | Verifies an exported proof using the owner API and prints the verification result. Accepts `--content JSON` instead of a filename. |
| `scan [--start_height N] [--delete_unconfirmed]` | Reconciles wallet outputs with the node, starting at height 1 by default. Deletion is an explicit option because it changes unconfirmed records and locks. |
| `rewind_hash --out FILE` | Exports a private viewing credential. It allows viewing/scanning, not spending. |

The invoice recipient uses `pay`; the invoice issuer completes it through the
Foreign API's `finalize_invoice_tx`, using a wallet application that supports
that operation. This owner-only CLI intentionally stops at the owner API boundary.

## An exchange withdrawal test

First [fund the test wallet from the Floonet faucet](#3-get-floonet-test-coins-and-start-the-wallet-listener)
and leave the node and owner listener running. The example below uses **1440
confirmations**; newly received faucet outputs will not be eligible until they
reach that threshold. For a quicker Floonet-only exercise, consistently use
your chosen smaller test threshold in `info`, the estimate and `send`.

Use a separate test wallet as the recipient. In another operating-system
terminal, initialize it once and display its address:

```sh
export MWC_RECIPIENT_DIR="$HOME/mwc-api-test/recipient"
mwc-wallet --floonet --top_level_dir "$MWC_RECIPIENT_DIR" init
```

Configure its `check_node_api_http_addr` and `node_api_secret_path` as in step 2,
using the same running Floonet node. Then run:

```sh
mwc-wallet --floonet --top_level_dir "$MWC_RECIPIENT_DIR" address
```

Copy the value labeled **Tor/SlatepackTor address**. No owner listener is needed
for this recipient: its native CLI will receive the Slatepack file. Back at the
sender's JavaScript CLI prompt, open the wallet if it is closed, then estimate:

```text
open
info --min_conf 1440
send 1.0 --estimate --min_conf 1440 --change_outputs 3
```

For the next command, replace `RECIPIENT_ADDRESS` with that wallet's actual
56-character Slatepack address:

```text
send 1.0 --dest withdrawal.slatepack --slatepack_recipient RECIPIENT_ADDRESS --late-lock --min_conf 1440 --change_outputs 3
```

After confirming, expect two files: `withdrawal.slatepack` to deliver, and
`withdrawal.slatepack.recovery.json` to retain privately. The response JSON names
both paths. With late locking, the wallet selects inputs later, so other
withdrawals can change the available balance before this one is finalized.

In the recipient's operating-system terminal, change to the directory where
the sender CLI wrote `withdrawal.slatepack`. On separate machines, transfer
that file to the recipient first. Run:

```sh
mwc-wallet --floonet --top_level_dir "$MWC_RECIPIENT_DIR" receive --file withdrawal.slatepack --outfile response.slatepack
```

Expect `Response file response.slatepack generated` and a successful receive
command. Return this response file to the sender's working directory. Receipt
alone does not post the payment: the sender must finalize it. At the sender's
JavaScript prompt, inspect the response and complete the transaction:

```text
unpack --file response.slatepack
finalize --file response.slatepack --dest finalized.json --nopost
post --input finalized.json
```

Confirm the displayed transaction UUID and amount. `--nopost` deliberately
separates finalization from broadcasting for this walkthrough. If you omit
`--nopost`, `finalize` posts automatically after saving the result.

Use the real UUID shown in the response/checkpoint to track the transaction:

```text
txs --txid TRANSACTION_UUID
```

For exchanges, retain your internal withdrawal ID → slate UUID → wallet
transaction ID mapping. Reconcile chain confirmation and transaction state
before crediting a deposit or marking a withdrawal complete. The
[exchange integration recommendations](https://github.com/mwcproject/mwc-node/blob/master/doc/exchange_recommendations.md)
cover Slatepack, late locking, change outputs and the 1440-confirmation policy.

## Calling any remaining owner API method

`rpc` is for developers who need the exact API parameters. It calls only methods
in the current `OwnerRpcV3` interface. **Every declared method parameter is
available**, including nested transaction arguments, configurations, queries,
slates, proofs, recipient addresses and address indexes. The convenience
commands implement common workflows; `rpc` gives access to the complete API.

`help rpc` lists callable methods. For a particular method, use either:

```text
help rpc retrieve_outputs
rpc retrieve_outputs --help
```

Supply parameters in any of these forms:

| Option | Input |
| --- | --- |
| `--params FILE` | A file containing a JSON object with the API's named parameters. |
| `--params-json JSON` | The same object, directly on the command line. |
| `--param NAME=JSON` | One parameter; repeat for additional distinct parameters. |

Use one base object, from either a file or inline JSON. Additional `--param`
options may add parameters absent from that object. Duplicate parameters and
unknown top-level names are rejected. Nested structures pass through unchanged;
the wallet API validates their fields and values.

These commands are equivalent at an open wallet's prompt:

```text
rpc retrieve_outputs --params-json '{"include_spent":true,"refresh_from_node":false,"tx_id":12}'
rpc retrieve_outputs --param include_spent=true --param refresh_from_node=false --param tx_id=12
```

The API will return outputs associated with wallet transaction ID 12; replace
it with an actual ID, or pass `tx_id=null` to list all outputs. JSON strings
require double quotes inside the shell/prompt quoting:

```text
rpc create_account_path --param 'label="exchange deposits"'
rpc query_txs --param refresh_from_node=false --param 'query={"limit":20,"sort_field":"Id","sort_order":"Desc","exclude_cancelled":true}' --param show_last_four_days=false
```

The first command asks for confirmation before creating the account. The
second queries transaction history. Use JSON objects/arrays for complex
parameters, for example `--param 'args={...}'` with a complete `InitTxArgs`
object or `--param 'slate="COMPLETE_SLATEPACK"'` for an API accepting a Slatepack.
Amounts inside API objects are nanoMWC, normally decimal strings; the
[transaction argument example](readme.md#amounts-and-transaction-construction)
shows their types. Use `--params FILE` for secret-bearing values to keep them
out of shell history and operating-system command arguments.

The client manages the session token, JSON-RPC version, request IDs, encryption
nonces and ephemeral ECDH keys. Omit `token`; `init_secure_api` runs automatically.
Transaction selectors such as `tx_id` and IDs nested in transaction objects
remain caller-controlled. `rpc open_wallet` accepts `name` and `password`
parameters and updates the CLI's session; omitting `password` uses the hidden
prompt/environment input. Its result displays wallet status and keeps the token
private. `rpc close_wallet` closes this session's wallet, using the opened name
unless a matching `name` is supplied. A one-command invocation still closes any
wallet it opened on exit.

For example, create this file in your operating-system terminal, outside the
interactive CLI:

```sh
cat > query.json <<'JSON'
{
  "refresh_from_node": false,
  "query": {
    "limit": 20,
    "sort_field": "Id",
    "sort_order": "Desc",
    "exclude_cancelled": true
  },
  "show_last_four_days": false
}
JSON
```

At the open wallet's prompt:

```text
rpc query_txs --params query.json --out recent-transactions.json
```

Expect a new private JSON file containing `[refreshed, transactions]`. The CLI
injects its current token; **omit `token` from parameter files**. Mutating
methods require confirmation or `--yes`. Lifecycle mutations such as
`create_wallet`, `change_password`, `delete_wallet`, `create_config` and
`set_top_level_directory` require this session's wallet to be closed.

`get_mnemonic`, `get_rewind_hash` and `build_output` return secret-bearing data;
`rpc` requires `--out` for them and does not print those results to the terminal.
Credential-bearing parameter files must be private as well. Treat `rpc` as the
low-level interface: it does not automatically perform the multi-call validation,
locking, checkpointing or posting workflow of the named commands. Use the named
commands for the illustrated exchange flows and `rpc` for deliberate API tests.

For complete parameter structures, see the
[owner API examples](../../../api/src/owner_rpc_v3.rs) and
[JavaScript method wrappers](src/examples.js). The [client reference](readme.md)
explains every method group and the encryption protocol.

## Failure handling and logs

A timed-out request may already have changed the wallet or reached the node.
The CLI does not retry, rekey, cancel or roll back it automatically. After a
transport failure, inspect the wallet and node before repeating an operation.
Use the transaction UUID to reconcile an in-progress withdrawal.

Output files are reserved before transaction-changing operations. If a later
step fails, a file can be empty or contain a partial workflow checkpoint. For
send/invoice/pay/finalize, inspect `FILE.recovery.json`; it records the returned
slate when that stage completed. Preserve these files until the transaction is
reconciled. Existing filenames are rejected on a subsequent attempt so a retry
does not silently overwrite the evidence of an earlier attempt.

| Symptom | Next action |
| --- | --- |
| `Missing script: cli` | Check the source checkout and sample directory. `package.json` must contain `scripts.cli`. |
| HTTP 401 | Match `MWC_OWNER_API_SECRET_FILE` to this wallet's `api_secret_path`. |
| `get_tip` / node connection failure | Start/synchronize mwc-node; check wallet `check_node_api_http_addr` and `node_api_secret_path`. |
| Node reports `Access denied` / invalid foreign API secret | Make the wallet's node-secret file contain the same secret as the node's configured `.foreign_api_secret`; restart the wallet listener. This is separate from the owner API secret. |
| Wrong password / wallet RPC error | Check the wallet log at the path printed in the error. Verify the password/network/directory. |
| Balance is cached (`refreshed: false`) | Inspect node connectivity; rerun `info` after resolving it. |
| Insufficient funds | Check confirmations, selected account, pending locks and fees. Late locking still requires funds at finalization. |
| Output file already exists | Inspect it and any recovery checkpoint before selecting a new filename. |
| Invalid Slatepack purpose, direction or sender | Obtain the correct response for the intended transaction; do not bypass these checks to force finalization. |
| Session lost | Another client may have rekeyed the listener, or transport/authentication failed. Reconcile the previous request before reconnecting. |
| Close not confirmed | Inspect the dedicated owner listener; the client cannot claim the wallet is closed. |

The sample wallet's server log normally lives at
`$HOME/mwc-v3-sample/mwc-wallet.log`; the authoritative setting is
`[logging].log_file_path`. Override `MWC_WALLET_LOG_FILE` if it differs. Outgoing
JSON requests are printed by default. To include decrypted responses as well,
enable debug tracing before starting the CLI:

```sh
export MWC_API_DEBUG=1
npm run cli
```

Traces are redacted and written to standard error. They can still contain
balances, addresses and transaction history; keep them private. Use
`unset MWC_API_DEBUG` to return to request-only output. To suppress request
records too, set `export MWC_API_REQUESTS=0` before starting; unset it to restore
the default. Debug mode (`MWC_API_DEBUG=1`) takes precedence and prints both.
The [logging reference](readme.md#log-locations-and-requestresponse-traces)
shows how to save a private diagnostic file. Default HTTP request timeout is
60 seconds; use `export MWC_API_TIMEOUT_MS=300000` before a long scan if needed.

## Testing and understanding the JavaScript code

```sh
npm test
```

Expect all tests to pass. They use mock wallets on temporary loopback ports,
public test fixtures, and temporary files. They exercise API encryption,
password input, command parsing, amount precision, confirmations, transaction
call ordering, file conflicts, failed calls, and secret redaction. They do not
spend real coins or establish that every operation succeeds against a live node.
Use Floonet for an end-to-end transaction test.

JavaScript concepts needed to read this sample:

| Syntax | Meaning in this project |
| --- | --- |
| `require('./client')` | Load another local JavaScript file. |
| `const x = ...` | Create a variable whose binding will not be reassigned. |
| `{ token, refresh_from_node: true }` | An object with named fields; serialized to JSON API parameters. |
| `null`, `true`, `false` | JSON-compatible absence/boolean values. They are not quoted strings. |
| `async` / `await` | Wait for an asynchronous API operation before continuing. The CLI sends commands sequentially. |
| `try` / `catch` / `finally` | Handle failures and perform cleanup, including closing the wallet. |
| `BigInt` | Exact integer arithmetic for MWC amounts; avoids floating-point rounding. |
| `process.env` | Environment variables configured by `export` in the shell. |
| `#token` | A private JavaScript class field; it is not included in normal object printing. |

The files are divided by responsibility:

1. [`cli.js`](src/cli.js) loads configuration, runs the prompt or one command,
   and closes the session.
2. [`cli_commands.js`](src/cli_commands.js) defines accepted commands and maps
   them to owner API calls. `WalletSession` holds the wallet token and workflows.
3. [`cli_io.js`](src/cli_io.js) handles hidden input, file safety, terminal-safe
   output and exact amount conversion.
4. [`client.js`](src/client.js) implements authenticated encrypted JSON-RPC and
   HTTP/HTTPS. Callers receive decoded `result.Ok` values or an exception.
5. [`logging.js`](src/logging.js) produces bounded, redacted diagnostic traces.
6. [`examples.js`](src/examples.js) shows named JavaScript parameters for all
   current owner methods. [`index.js`](src/index.js) is the automatic query demo
   still available through `npm start`.
7. [`cli_rpc.js`](src/cli_rpc.js) lists the API's parameter names and combines
   file, inline-object and individual parameter input. Its coverage test compares
   every method and parameter against the Rust `OwnerRpcV3` trait.

To add an owner-supported convenience command, add its help/option definition
in `COMMANDS`, its handler in `WalletSession.execute`, and tests for its API
sequence and failure cases. Reuse `OutputFile` for exports, keep tokens private,
and let the Rust wallet perform transaction cryptography. Extend this guide
with its purpose, inputs, side effects and expected result.
