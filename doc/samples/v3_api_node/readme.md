# Node.js client for the wallet v3 owner API

This sample connects to **mwc-wallet**, at `/v3/owner`. It handles HTTP Basic
authentication, the `init_secure_api` handshake and encrypted JSON-RPC calls.
It includes examples for all **38 methods** in the current
[`OwnerRpcV3` interface](../../../api/src/owner_rpc_v3.rs).

**Start with the [CLI guide](cli.md) if you are new to MWC or JavaScript.** It
explains the node/wallet/client relationship, installation prerequisites, a
complete first session, every CLI command, exchange workflows and troubleshooting.
You can use the interactive CLI without writing JavaScript. This page describes
the reusable client, the automatic query example and the API protocol.

Use Node.js **22 or newer**. The implementation uses Node's built-in HTTP, TLS,
crypto and test modules; there are no npm dependencies to install.

| File | Purpose |
| --- | --- |
| [`src/client.js`](src/client.js) | Reusable `OwnerClient`: authentication, encryption, transport and response validation. |
| [`src/index.js`](src/index.js) | Runnable example: open a wallet, query accounts/height/balance/outputs/transactions, then close it. |
| [`src/cli.js`](src/cli.js) | Interactive and single-command CLI; start with `npm run cli`. |
| [`src/cli_commands.js`](src/cli_commands.js) | Command definitions and owner API workflows. |
| [`src/cli_io.js`](src/cli_io.js) | Hidden password input, exact amounts, argument parsing and private output files. |
| [`src/cli_rpc.js`](src/cli_rpc.js) | Complete v3 parameter coverage and file/inline JSON parameter input. |
| [`src/examples.js`](src/examples.js) | One named function per owner method, with the current parameter names and optional defaults. Importing it executes nothing. |
| [`src/logging.js`](src/logging.js) | Redacts and bounds optional diagnostic request/response traces. |
| [`test/client.test.js`](test/client.test.js) | Local mock-server tests, security failure cases and Rust wire-format compatibility. |
| [`test/cli.test.js`](test/cli.test.js) | CLI workflows, hidden passwords, exact amounts, file protection and failure recovery tests. |

## 1. Run the local tests

From this directory:

```sh
npm test
```

Expect all tests to pass and the process to exit with code 0. Tests create
short-lived HTTP servers on `127.0.0.1`, using synthetic credentials and
wallet responses. They do not require a wallet, node, coins or Internet access.
Allow local loopback sockets if running in a sandbox.

The suite checks:

- Basic authentication, ECDH and encrypted open/query/close calls.
- JavaScript encryption against a request generated by the Rust API, and
  decryption of a Rust-generated response.
- Authentication failure, invalid public keys, changed IDs/versions, altered
  ciphertext/tags, malformed nonces/base64, reflected messages and replay under
  a different request ID.
- Concurrent-call rejection, disposal, timeouts, response-size limits, refused
  redirects and exact handling of large integers.
- Absence of credentials from the command's output.
- Coverage of every current Rust owner method and its named parameters.
- CLI transaction ordering, confirmation prompts, exclusive private files,
  recovery checkpoints, hidden passwords and one-command session cleanup.

The Rust compatibility data is in [`test/fixtures/wire.json`](test/fixtures/wire.json);
[`generate_wire.rs`](test/fixtures/generate_wire.rs) records how it was generated
using `mwc_wallet_api::EncryptedRequest` and `EncryptedResponse`.

## 2. Start a dedicated Floonet owner listener

**mwc-node must be started and connected to Floonet.** Keep it running while
testing: mwc-wallet connects to the node to refresh balances, scan and post
transactions. Follow the [node setup steps](cli.md#1-start-a-node-in-terminal-a)
if you do not already have a running Floonet node.

Use a disposable, initialized Floonet wallet. The example opens and closes that
wallet, so give it a dedicated listener. A new wallet can be created with:

```sh
# Choose a new directory for this test wallet.
export MWC_SAMPLE_WALLET_DIR="$HOME/mwc-v3-sample"
mwc-wallet --floonet --top_level_dir "$MWC_SAMPLE_WALLET_DIR" init
```

Choose a test password and save the recovery phrase when prompted. The command
creates `mwc-wallet.toml`, the API secret files and wallet data in this directory.
For an existing test wallet, set the variable to the directory containing its
configuration instead.

In that wallet's `[wallet]` configuration, keep the listener dedicated to the
owner client:

```toml
owner_api_include_foreign = false
owner_api_include_mqs_listener = false
check_node_api_http_addr = "http://127.0.0.1:13413"
```

Keep `api_secret_path` configured. Its file contains the **owner API** secret;
`node_api_secret_path` is a different credential used to contact the node.
Set `node_api_secret_path` to the actual node's `.foreign_api_secret` file. A new
wallet in a separate directory may generate its own file with that name; its
contents must match the node. If node and wallet use separate
`.foreign_api_secret` files, **copy the node's secret to the wallet's file so
both contain the same secret**. Keep the owner API secret separate. The
[wallet configuration steps](cli.md#2-create-and-configure-a-wallet-in-terminal-b)
show both the shared-path and copied-file setup. Start and synchronize the
Floonet node before refreshing wallet data.

For payment tests, request Floonet coins before starting the wallet listener:

```sh
# Keep mwc-node running; run these while this wallet's owner listener is stopped.
mwc-wallet --floonet --top_level_dir "$MWC_SAMPLE_WALLET_DIR" faucet_request --amount 3
mwc-wallet --floonet --top_level_dir "$MWC_SAMPLE_WALLET_DIR" info
```

Enter the wallet password when prompted. The faucet command requests 3 test MWC,
finalizes and posts the transaction. Expect `Command 'faucet_request' completed
successfully`. `info` refreshes the balance from the node; the coins become
**Currently Spendable** after the required confirmations (10 by default).
Requests are capped at 5 MWC. See the
[funding walkthrough](cli.md#3-get-floonet-test-coins-and-start-the-wallet-listener)
for confirmation waits, faucet troubleshooting and restarting an existing
listener. No coins are needed for connection and query tests.

Start the owner listener in a separate terminal from the node:

```sh
mwc-wallet --floonet --top_level_dir "$MWC_SAMPLE_WALLET_DIR" owner_api
```

Leave the listener running. The Node.js client supplies the wallet password to
`open_wallet`. The wallet's configured node must be reachable and synchronized
for a successful balance refresh. An empty test wallet is sufficient to test
the API connection; it does not need coins.

## 3. Run the example against that wallet

In another terminal, leaving both node and wallet listener running, from this
sample directory:

```sh
export MWC_OWNER_API_URL='http://127.0.0.1:13420/v3/owner'
export MWC_OWNER_API_SECRET_FILE="$HOME/mwc-v3-sample/.owner_api_secret"

# Read the test password without echoing it or putting it in shell history.
# The password exists only in this child shell and its Node.js process.
bash -c 'read -r -s -p "Test wallet password: " MWC_WALLET_PASSWORD; printf "\n"; export MWC_WALLET_PASSWORD; npm start'
```

Use the actual `api_secret_path` if it differs from the example. Pressing Enter
at the password prompt explicitly supplies an empty password.

Expect `Secure session established; wallet opened.`, a small JSON summary, and
`Wallet closed.` The summary contains account/output/transaction counts, node
height, refresh flags, and balances in **nanoMWC**. An empty wallet normally has
zero balances and no transactions. `wallet_refreshed: true` means the balance
query refreshed successfully from the node; `false` means the returned wallet
data was not validated by that refresh. `node_contacted` describes the separate
`node_height` call.

The command refreshes once, then queries cached outputs and transactions. Refresh
performs the wallet's normal reconciliation; its behavior follows the wallet's
configured replay-protection settings. None of the transaction-construction,
posting, password-change or deletion examples run from `npm start`.

| Setting | Meaning / default |
| --- | --- |
| `MWC_OWNER_API_URL` | Owner endpoint; defaults to `http://127.0.0.1:13420/v3/owner` (Floonet). Mainnet normally uses port 3420. |
| `MWC_OWNER_API_SECRET_FILE` | Required path to the configured owner secret file. Read locally; its content is never logged. |
| `MWC_WALLET_PASSWORD` | Required for `npm start`, including an explicit empty string for an empty password. Optional for the CLI, which otherwise uses a hidden terminal prompt. Removed from the Node process environment after loading. |
| `MWC_API_TIMEOUT_MS` | Total time allowed per HTTP request; defaults to 60000 ms. Increase it for a slow initial refresh, for example `export MWC_API_TIMEOUT_MS=300000`. |
| `MWC_WALLET_LOG_FILE` | Optional wallet-server log path to include in RPC errors. Defaults to `mwc-wallet.log` beside the owner secret file, labeled as the default location. Override it to match `[logging].log_file_path` when customized or when using a remote wallet. |
| `MWC_API_DEBUG` | Set to `1` to write redacted JSON-RPC request/response bodies to standard error. Disabled by default; the CLI still prints requests unless suppressed below. |
| `MWC_API_REQUESTS` | CLI only: outgoing JSON requests are printed by default. Set to `0` to suppress them when debug mode is off. |
| `NODE_EXTRA_CA_CERTS` | Optional PEM CA file for a private HTTPS certificate; set before starting Node.js. |

For HTTPS, use a URL whose hostname matches the certificate. The client requires
normal certificate verification. See [wallet TLS setup](../../tls-setup.md) for
listener configuration and binding details.

## Using the client in your code

`connect()` establishes the secure session. `call(method, params)` sends one
encrypted request and returns the contents of `result.Ok`; it throws on HTTP,
protocol, authentication or wallet errors. Functions in `examples.js` forward
the same named parameters:

```js
const { OwnerClient } = require('./src/client');
const api = require('./src/examples');

// options contains { url, secret }; password comes from your secret input.
async function readBalance(options, password) {
  const client = new OwnerClient(options);
  let opened = false;
  try {
    await api.init_secure_api(client);
    const token = await api.open_wallet(client, { password });
    opened = true;
    const [refreshed, balance] = await api.retrieve_summary_info(client, {
      token, refresh_from_node: true, minimum_confirmations: 10,
    });
    return { refreshed, spendable: BigInt(balance.amount_currently_spendable) };
  } finally {
    try {
      if (opened) await api.close_wallet(client);
    } finally {
      client.dispose();
    }
  }
}
```

Retain the returned `token` in memory and pass it to methods that require it.
It is the wallet keychain mask, not the HTTP Basic password or the AES session
key. `close_wallet` takes `name` (normally `null`), **not a token**. Report cleanup
failures in your application: a failed close does not establish that the wallet
is closed. `dispose()` clears local client state; it does not make an API call.

Await calls sequentially. The listener maintains one shared secure-session key;
a second client's handshake replaces it. Coordinate access to a dedicated
listener. A new session is needed after 65,536 encrypted requests. Open/close
and handshake operations are individual requests, not JSON-RPC batches or
notifications.

### Query outputs and transaction history

```js
// Include spent outputs when inspecting wallet history.
const [outputsRefreshed, outputs] = await api.retrieve_outputs(client, {
  token, include_spent: true, refresh_from_node: false, tx_id: null,
});

// Retrieve one transaction by wallet-local ID or by slate UUID.
const [txsRefreshed, txs] = await api.retrieve_txs(client, {
  token, tx_id: 12, tx_slate_id: null, show_last_four_days: false,
});

// Request a bounded page. Use the last ID as the next page's boundary.
const [pageRefreshed, page] = await api.query_txs(client, {
  token,
  query: { min_id: 0, limit: 20, sort_field: 'Id', sort_order: 'Asc', exclude_cancelled: true },
});
```

`retrieve_summary_info`, `retrieve_outputs`, `retrieve_txs` and `query_txs`
return `[refreshed, data]`. With `refresh_from_node: false`, use the data as a
cached view. A wallet-local transaction `id` is different from `tx_slate_id`, the
transaction's slate UUID. `get_stored_tx` uses a locator such as
`{ id: 12 }` or `{ tx_slate_id: slateId }`; provide matching identifiers if you
supply more than one.

### Amounts and transaction construction

Amounts are in nanoMWC: `1 MWC = 1000000000` nanoMWC. Use decimal strings for
amount fields and `BigInt` for calculations. Pass ordinary small integers for
RPC arguments such as `minimum_confirmations`, `tx_id` and `address_index`.
The client rejects unsafe outgoing JavaScript numbers and preserves oversized
integer literals in responses as decimal strings.

This example asks for a fee estimate; it supplies `estimate_only: true`:

```js
const sendArgs = {
  src_acct_name: null,
  amount: '1000000000',
  amount_includes_fee: false,
  minimum_confirmations: '10',
  max_outputs: 500,
  num_change_outputs: 1,
  selection_strategy_is_use_all: false,
  message: null,
  target_slate_version: 4,
  ttl_blocks: '1440',
  payment_proof_recipient_address: null,
  address: null,
  estimate_only: true,
  exclude_change_outputs: false,
  minimum_confirmations_change_outputs: 10,
  send_args: null,
  outputs: null,
  slatepack_recipient: null,
  late_lock: false,
  min_fee: null,
};
const estimate = await api.init_send_tx(client, { token, args: sendArgs });
```

The `InitTxArgs.minimum_confirmations` field accepts a decimal string through its
Rust serializer; the top-level `retrieve_summary_info.minimum_confirmations`
argument is a JSON number. The sample's 10-confirmation threshold is an example
setting; choose the policy appropriate to your integration.

For an intentional Slatepack withdrawal, use `estimate_only: false`,
`late_lock: true`, and a recipient address obtained through your application's
validated recipient selection. `num_change_outputs` controls the target number
of change outputs. `send_args: null` leaves Slatepack delivery to your application.

The sender's flow is:

1. `init_send_tx` creates the initial slate and persists its transaction context.
2. `encode_slatepack_message` with `content: 'SendInitial'` and the recipient's
   Slatepack address returns the message to deliver.
3. `decode_slatepack_message` decodes the recipient's reply. Check its `content`
   (`SendResponse`), sender, slate ID, amount and expected transaction before
   accepting it. `verify_slate_messages` verifies participant messages.
4. `finalize_tx` finalizes the returned slate. Late locking selects/locks inputs
   at finalization; for an ordinary early-lock send, use `tx_lock_outputs` for
   participant 0 after initiation instead.
5. `get_stored_tx` with `{ tx_slate_id: slateId }` retrieves the finalized
   transaction; pass that transaction to `post_tx` to broadcast it. Track it with
   `retrieve_txs`/`query_txs` until confirmed.

For example, the encoding call is:

```js
const message = await api.encode_slatepack_message(client, {
  token, slate, content: 'SendInitial', recipient: recipientAddress, address_index: null,
});
```

A timeout after a transaction-changing request has an **unknown outcome**. The
client does not automatically retry. Reconcile the stored transaction and node
state before deciding the next action. Cancel an abandoned, unconfirmed
transaction using `cancel_tx` with its ID or UUID.

Receiving a normal send uses the recipient wallet's Foreign API (`receive_tx`);
finalizing an invoice uses its `finalize_invoice_tx`. Those are separate from
this owner API client. Owner-side invoice calls are `issue_invoice_tx` and
`process_invoice_tx`. See the
[Foreign RPC interface](../../../api/src/foreign_rpc.rs) and
[transaction argument types](../../../libwallet/src/api_impl/types.rs) when
implementing the other side of the exchange.

## Complete owner API examples

Every method below is exported from `src/examples.js` under its exact RPC name.
Call it as `await api.method(client, { named_parameters })`. Optional arguments
have defaults in that file; required arguments are checked before sending.
Complex values such as slates, proofs and configurations retain their Rust JSON
structure. A function is an explicit API invocation, including mutations and
secret-bearing results; select the functions your application needs.

| Area | Methods and their purpose |
| --- | --- |
| Secure session | `init_secure_api`: calls `client.connect()`, which manages ephemeral ECDH keys. |
| Wallet lifecycle | `get_top_level_directory`, `set_top_level_directory`: inspect/select the wallet configuration directory. `create_config`: write configuration for a `chain_type`, e.g. `Floonet`. `create_wallet`: create or recover using `mnemonic`, `mnemonic_length` and `password`. `open_wallet`, `close_wallet`: manage the active wallet and token. |
| Secret management | `get_mnemonic`: returns the recovery phrase. `change_password`: takes `old` and `new`. `delete_wallet`: deletes wallet data. Run these only as explicit application actions; handle returned secrets privately. |
| Accounts | `accounts`: list labels/paths. `create_account_path`: create a label. `set_active_account`: select a label for subsequent operations. |
| Wallet data | `retrieve_summary_info`, `retrieve_outputs`, `retrieve_txs`, `query_txs`: balance, outputs and transaction history. `node_height`: node height and whether the node was contacted. |
| Sender | `init_send_tx`, `tx_lock_outputs`, `finalize_tx`, `post_tx`, `cancel_tx`, `get_stored_tx`, `verify_slate_messages`: construction, locking, completion, broadcast and transaction inspection. |
| Invoices | `issue_invoice_tx`: create an invoice with `IssueInvoiceTxArgs`. `process_invoice_tx`: fund an invoice with `InitTxArgs`; invoice processing rejects fee-estimate, TTL and payment-proof-recipient options. |
| Slatepack and addresses | `get_wallet_public_address`, `get_mqs_address`: current public addresses. `encode_slatepack_message`, `decode_slatepack_message`: encode/decode a slate and its purpose, with optional `address_index`. |
| Payment proofs | `retrieve_payment_proof`: obtain a proof by transaction ID/UUID. `verify_payment_proof`: verify its content and ownership information. |
| Recovery/viewing | `scan`: reconcile outputs from `start_height`, with explicit `delete_unconfirmed` behavior. `get_rewind_hash`: return a private viewing credential. `scan_rewind_hash`: scan a view wallet; its result is not proof of spend ownership. |
| Advanced configuration/output | `set_tor_config`: configure wallet Tor behavior. `build_output`: construct an output from `features` and nanoMWC `amount`; its response contains sensitive blinding data. |

For example, account creation is
`await api.create_account_path(client, { token, label: 'deposits' })`.
Creating a wallet uses `mnemonic_length: 32` for 32 bytes of entropy (24 words),
or 16 for 12 words; this argument is not the word count. For recovery, supply
`mnemonic` through your protected secret input. See the linked Rust interface
for each method's complete parameter and response examples.

## Wire protocol

1. Each HTTP request authenticates with `Authorization: Basic base64(mwc:secret)`.
2. `init_secure_api` exchanges compressed secp256k1 public keys. The 32-byte raw
   ECDH x-coordinate is the AES-256 key, matching the current Rust protocol.
3. The inner request contains `jsonrpc`, a unique string `id`, `method`, and
   named `params`. AES-256-GCM encrypts its UTF-8 JSON.
4. The outer method is `encrypted_request_v3`. Its `params` contain a 12-byte
   nonce encoded as 24 hex characters and `body_enc`, which is
   `base64(ciphertext || 16-byte authentication tag)`.
5. The response body is in `result.Ok`. After authenticating/decrypting it, the
   client checks the inner JSON-RPC response and returns its `result.Ok`.

GCM additional authenticated data (AAD) binds the envelope metadata. Each of
these fields is prefixed with its **8-byte big-endian byte length**, then the
UTF-8 bytes, in this order:

| Field | Request | Response |
| --- | --- | --- |
| Domain | `mwc-owner-api-v3` | `mwc-owner-api-v3` |
| Direction | `request` | `response` |
| JSON-RPC version | `2.0` | `2.0` |
| Method | `encrypted_request_v3` | `encrypted_response_v3` |
| ID type | `string` | `string` |
| ID value | Request's unique string ID | The same ID |

`encrypted_response_v3` is an AAD constant; the response envelope has no `method`
field. The client uses monotonic string IDs and a random session nonce prefix
plus an incrementing counter, so IDs and nonces are never reused within a session.
The implementation follows the serializers in
[`api/src/types.rs`](../../../api/src/types.rs) and the request handling in
[`controller/src/controller.rs`](../../../controller/src/controller.rs).

## Security properties and operating limits

The client accepts plain HTTP only for literal loopback addresses and requires
verified HTTPS elsewhere. ECDH encryption alone does not authenticate the server;
use a trusted local listener or verified TLS. Redirects are refused, credentials
are kept in private client fields, and default errors omit server-supplied text
that could echo secrets. Requests have a total timeout and an 8 MiB size limit;
`OwnerClient` accepts `timeoutMs` and `maxResponseBytes` overrides (up to 64 MiB).
Prefer bounded queries for large histories.

A response is used only after its GCM tag, envelope ID/version and inner ID/version
have been checked. Transport or protocol failures discard the local AES key.
The client sends no automatic retries and accepts only one in-flight request.
Fresh handshakes create fresh ECDH keys. `dispose()` wipes the AES key buffer and
clears the stored authorization header.

JavaScript strings, environment variables and runtime-managed crypto allocations
cannot be reliably erased from process memory. Keep this process on a trusted
host, restrict secret-file access, and avoid debugger/heap dumps in a real wallet
integration. The printed balances are private wallet information too. These
checks and tests establish specific properties of this sample; they are not a
complete security audit of an application built around it.

## Troubleshooting

### Log locations and request/response traces

The wallet's `[logging].log_file_path` in `mwc-wallet.toml` controls its server
log. For the test wallet created above, that path is
`$HOME/mwc-v3-sample/mwc-wallet.log`. File logging requires `log_to_file = true`.
RPC errors include the default path derived from the owner secret directory;
set `MWC_WALLET_LOG_FILE` to the configured path if it differs. For example:

```sh
export MWC_WALLET_LOG_FILE="$HOME/mwc-v3-sample/mwc-wallet.log"
tail -n 50 "$MWC_WALLET_LOG_FILE"
```

Look for errors at the time of the failed request. For example, `Error calling
get_tip` with a connection failure for `http://127.0.0.1:13413/v2/foreign` means
the wallet could not contact its configured Floonet node. Check that node's
listener and the wallet's `check_node_api_http_addr` configuration.

The Node.js sample can also trace the decrypted JSON-RPC bodies it sends and
receives. The CLI prints redacted outgoing requests by default; the automatic
`npm start` example enables tracing only when requested. These diagnostics are
separate from the wallet server's log:

```sh
export MWC_API_DEBUG=1
# Repeat the password-prompt/npm-start command from step 3.
```

Each `[wallet-api]` line includes `direction`, `method`, and `body`. Responses
are traced after decryption and authentication; an application error includes
its code and redacted message. Password/configuration requests and secret-bearing
responses are suppressed, nested credential fields are redacted, and known
request credentials are removed from echoed text. HTTP authorization headers
and AES keys are never traced. Large values are truncated. Other wallet data,
including balances, addresses and transaction history, can appear in a trace.

To save the trace locally, use a private file from this sample directory:

```sh
bash -c 'umask 077; read -r -s -p "Test wallet password: " MWC_WALLET_PASSWORD; printf "\n"; export MWC_WALLET_PASSWORD; MWC_API_DEBUG=1 npm start 2>"$HOME/mwc-v3-sample/nodejs-api-debug.log"'
```

Inspect `$HOME/mwc-v3-sample/nodejs-api-debug.log` for the failing method's request
and response. Adjust that path if you used a different test-wallet directory.
Keep it private. `unset MWC_API_DEBUG` disables response tracing for subsequent
CLI runs and all tracing for `npm start`. To also suppress the CLI's default
request records, set `MWC_API_REQUESTS=0`.
When importing `OwnerClient`, pass `walletLogFile` and optionally a
`trace: (line, direction) => ...` callback; the callback receives only the
redacted trace and its `request`/`response` direction.

| Result | What to check |
| --- | --- |
| HTTP 401 | `api_secret_path`, its file contents and Basic username `mwc`; use the owner secret. |
| Connection or TLS failure | Owner listener is running; URL/network/port are correct; certificate hostname and CA are trusted. |
| Response authentication failure | Client and wallet use the same AAD protocol; another client has not replaced the listener's session key. Establish a fresh session after resolving the cause. |
| Wallet RPC error | The numeric code is reported without echoing request values. Check the wallet log for password, lifecycle, parameter or node errors. |
| `wallet_refreshed: false` | Check the wallet's configured node URL, node secret, reachability and synchronization. |
| Timeout | A refresh may be slow. For a mutation, first reconcile its outcome; increasing a timeout does not make retrying safe. |
| Close not confirmed | Check the dedicated listener and wallet state before reusing it. Restart that listener if necessary. |

For a live test, run the Floonet example above, confirm refresh succeeds, and
compare its nanoMWC balances/counts with that test wallet's CLI output after the
owner listener is stopped. Exercise transaction workflows separately with test
coins and verify confirmation on Floonet. The local mock tests validate the
client and transport, not real transaction consensus or every server-side method.
